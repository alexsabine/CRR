# Declaration addendum: C8, does thread-scheduling fairness set the delayed-gratification level and its obstacle trend? (2026-10-14, 13:58Z; after C7's four movable cell-view lines were read, before any run of `checks/c8_scheduling_stickiness.py`)

**What prompted it.** C7's authors'-code runs (movable, cell-view bubble, 100 experiments each) give DG 0.391 / 0.389 / 0.389 / 0.384 for 0 / 1 / 2 / 3 frozen cells: flat, and above the paper's 0.24 → 0.37. C6's random-visiting engine gave 0.379 / 0.375 / 0.376 / 0.376: flat, same level. The classical baseline matches the paper (C6 0.084; the paper's traditional bubble about 0.08). So the between-engine agreement is good and the disagreement is with the paper's cell-view level and trend. One thing differs between this machine and the authors' and is not in the rules: **which thread gets the lock next.** In the authors' cells each thread spins `move()` with no sleep; the lock is Python's non-fair `threading.Lock`. On this Linux/CPython 3.13 the hand-off is nearly round-robin (a probe run: consecutive swaps by different cells 2 386 times in 2 504, and the trajectory is reproducible run to run given the seed). If on the authors' machine a thread that released the lock often re-acquired it at once, one cell would make several swaps in a row before another cell moved: a "sticky" schedule, which lies between the random-visit cell-view and the classical algorithm (where one index position is served in order).

**Design.** The C6 engine (`cellview`) with one added parameter, `sticky ∈ {0, 0.5, 0.9, 0.99, 1.0}`: after a cell swaps, with probability `sticky` it is visited again at once; otherwise a cell is drawn at random as in C6 (`sticky = 0` is C6 exactly). Cell-view bubble, movable frozen cells 0–3 placed with replacement, n = 100, 50 replicates per cell; the authors' DG on adjacent descents; `S` on inversions, descents and footrule; swaps; sorted fraction; mean consecutive-same-mover run length. Post-hoc diagnostic alongside, labelled as such: the same run-length statistic measured on 20 fresh experiments of the authors' threaded code at 0 and 3 frozen cells.

**Predictions.**
1. `sticky = 0` reproduces C6 within 0.02 at every frozen count (regression check).
2. DG at 0 frozen falls monotonically with `sticky` (longer floor-holding makes the cell-view process more like one cell bubbling to its place, whose local error trace is closer to the classical one).
3. There is a `sticky` level at which DG at 0 frozen lies within 0.05 of the paper's 0.24.
4. **The obstacle trend, hedged.** If at any `sticky` level the DG rises by at least 0.03 per frozen cell from 0 to 3 (the paper's slope is about 0.04), the published trend is a product of scheduling, and the mechanism is that a frozen cell ends a sticky cell's run (the cell swaps past it, or stops at it) so that increases are shorter and the following decreases relatively longer. If DG is flat in frozen count at every `sticky` level, scheduling does not explain the trend and it stays unexplained by the rules as read, the scheduling as modelled and the measure.
5. Inversions and footrule `S = 0` throughout (the theorem; bubble only).

**What it would mean.** Either outcome of 4 is reportable to the authors: the first says their headline obstacle effect is a property of the operating system's lock hand-off, not of the cells; the second says a faithful reimplementation and their own code on another machine do not show it, which calls for their saved trajectories. No outcome is evidence for CRR.
