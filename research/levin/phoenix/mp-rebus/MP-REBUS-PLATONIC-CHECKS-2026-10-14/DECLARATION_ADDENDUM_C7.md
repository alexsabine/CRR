6. **Mechanism of the trend, declared as a diagnostic rather than a claim.** Under the lock, one bubble swap changes the adjacent-descent count by −1 (the fixed pair) plus 0 or +1 at each of the two flanking pairs, so Δ ∈ {−1, 0, +1}; after the authors' de-duplication, an "increase" is a run of +1 swaps and a "decrease" a run of −1 swaps, and DG is the mean of (decrease run − increase run)/increase run over consecutive pairs. The diagnostic decomposes DG by frozen count into: number of episodes; mean increase-run length; mean decrease-run length; the share of the DG sum carried by the final episode; and the fraction of +1 swaps that occur within one cell of a frozen position. **Expectation (hedged):** the rise with frozen count is carried by longer decrease runs, concentrated in the late clean-up around frozen cells, with increase-run lengths unchanged; if instead increase runs shorten, the trend is a denominator effect.

## What the outcomes mean

Prediction 1 holding establishes that the published trend is reproducible from the committed code and is a property of their measure on these trajectories (the rulers in 4 showing, as before, that nothing goes backward globally). Its failing means the committed code does not reproduce the paper, which would itself be a finding to report to the authors. The diagnostic in 6 is what CRR's carrier discipline adds: it asks where on the array and when in the run the measured "patience" lives. No outcome is evidence for CRR.

## Correction recorded before the full run (after the one-experiment smoke test, 13:15Z)

The smoke test (numbers not reported) exposed two things in the authors' code that the runner must respect, and one runner setting that the first draft got wrong:

1. **The stopping rule and the swap rule disagree about frozen neighbours.** `BubbleSortCell.should_move` (which the driver's `no_cells_should_move` polls) counts a neighbour as a reason to move only if that neighbour is `ACTIVE`; `should_move_to` (which `move` uses) lets a cell swap with a `FREEZE` neighbour. So the driver may stop a run while an active cell still sits out of order against a frozen one; whether it does depends on how much time passes between the last active–active disorder vanishing and the next poll. The cells spin without sleeping (`MultiThreadCell.run`), so the 1 s poll of the authors' driver gives the frozen-adjacent clean-up far more time than the 0.05 s poll of the first runner draft. **The runner's default poll is therefore set to the authors' 1 s** (the 0.05 s setting is kept as an option and will be run as a labelled secondary arm to show the size of this stopping-rule effect). This supersedes the "poll interval 0.05 s" line above.
2. **The frozen-attempt counter is inert in the committed code.** `MultiThreadCell.swap` increments `frozen_swap_attempts` only when the *moving* cell is itself frozen; frozen threads are never started and `should_move_to` requires `self.status == ACTIVE`, so the counter stays 0. It is recorded but carries no information.
3. Nothing in the predictions changes. Prediction 5's "within 0.05 of C6" now refers to the 1 s-poll arm.
